Quero que você desenvolva uma aplicação web completa e interativa para representar visualmente, em 3D, toda a operação logística descrita nos arquivos Bizagi e nos documentos POP/Word presentes neste diretório.

IMPORTANTE:
Este é um trabalho grande e provavelmente não será concluído dentro de uma única sessão/contexto.

Portanto, desde o PRIMEIRO MOMENTO, trabalhe de maneira incremental e totalmente retomável.

NÃO tente fazer tudo de uma vez.
NÃO dependa da memória desta conversa para saber o que já foi feito.
O próprio repositório deve ser a fonte de verdade sobre o progresso.

==================================================
1. OBJETIVO DO PROJETO
==================================================

Quero uma aplicação web que funcione como um:

"MAPA 3D INTERATIVO DA OPERAÇÃO"

O sistema deve permitir que uma pessoa que não conhece a operação consiga:

- visualizar a operação completa;
- entender quais processos existem;
- entender como os processos se relacionam;
- visualizar quais áreas participam de cada processo;
- visualizar os atores internos e externos;
- acompanhar o fluxo passo a passo;
- entender decisões e bifurcações;
- identificar início e fim dos processos;
- entender quais sistemas são utilizados;
- entender quais documentos, planilhas, e-mails e canais são utilizados;
- visualizar handoffs entre setores;
- identificar dependências entre processos;
- clicar em qualquer processo e receber uma explicação detalhada de como ele funciona.

Não quero apenas um BPMN renderizado.

Quero transformar os processos BPMN em uma EXPERIÊNCIA VISUAL DA OPERAÇÃO.

A aplicação deve funcionar como se estivéssemos olhando para uma "cidade logística digital", onde setores, atores, sistemas, documentos e processos estão espacialmente organizados e ligados entre si.

0010 - TRANSBORDO IMPORTAÇÃO.bpm.zip

ATENÇÃO:

Não trate esses arquivos apenas como ZIPs contendo uma imagem.

Faça engenharia reversa da estrutura.

A estrutura observada dos arquivos Bizagi é semelhante a:

<arquivo>.bpm.zip
    ModelInfo.xml
    Participants.xml
    Preferences.bpp
    *.diag
    Users/
    ...

E cada arquivo .diag também é um arquivo ZIP.

Ao extrair o .diag podem existir arquivos como:

Actions.xml
BPSimData.xml
BPSimDataResult.xml
Diagram.xml
ExtendedAttributeValues.xml

Portanto:

1. extraia o .bpm.zip;
2. detecte todos os arquivos .diag;
3. trate cada .diag como ZIP quando aplicável;
4. extraia os XMLs internos;
5. analise principalmente Diagram.xml;
6. descubra:
   - pools;
   - lanes;
   - participantes;
   - atividades;
   - eventos;
   - gateways;
   - subprocessos;
   - sequence flows;
   - message flows;
   - nomes;
   - IDs;
   - posições;
   - relacionamentos;
   - eventuais atributos estendidos;
7. preserve os IDs originais sempre que forem úteis para rastreabilidade.

Não assuma a estrutura do XML sem verificar os arquivos reais.

Crie um parser robusto baseado no conteúdo encontrado.

Um processo só pode ser considerado "mapeado" quando existir:

[ ] arquivo Bizagi analisado
[ ] POP analisado
[ ] atividades extraídas
[ ] executores extraídos
[ ] sistemas extraídos
[ ] decisões extraídas
[ ] fluxo reconstruído
[ ] início identificado
[ ] término(s) identificado(s)
[ ] documentação textual criada
[ ] modelo JSON criado
[ ] rastreabilidade disponível
[ ] visualização funcionando

30. TESTES
==================================================

Crie testes principalmente para o parser.

Exemplo:

- .bpm.zip pode ser aberto;
- .diag é identificado como pacote;
- Diagram.xml é encontrado;
- atividades são extraídas;
- gateways são extraídos;
- flows possuem origem e destino válidos;
- IDs duplicados são detectados;
- atividades referenciadas inexistentes são detectadas;
- todos os 10 processos possuem um modelo normalizado;
- executores mencionados nas atividades existem no catálogo de atores.

Adicionar validação do JSON usando schema, preferencialmente Zod ou JSON Schema.

32. EXPLICAÇÃO DO PROCESSO
==================================================

A aplicação deve conseguir responder visualmente a perguntas como:

"Como funciona a importação?"

"Depois que o cliente pede, quem recebe?"

"Quando entra a Central de Operações?"

"Em quais processos aparece o Pátio C?"

"Quais processos usam WhatsApp?"

"Quais processos dependem de porto?"

"Quem passa a missão ao motorista?"

"Onde existem decisões?"

"Quais são os possíveis finais?"

"Que processos compartilham as mesmas áreas?"

Essa capacidade deve vir do modelo estruturado,
não de respostas hardcoded.

34. QUANDO O CONTEXTO ESTIVER ACABANDO
==================================================

Se perceber que não haverá contexto suficiente para terminar:

NÃO tente correr e fazer várias coisas pela metade.

Faça o seguinte:

1. termine a menor unidade de trabalho possível;
2. execute os testes relacionados;
3. atualize TASKS.md;
4. atualize PROJECT_STATUS.md;
5. atualize .codex/HANDOFF.md;
6. registre eventuais decisões em DECISIONS.md;
7. faça checkpoint em Git se apropriado;
8. pare em um estado executável.

O HANDOFF deve terminar com uma instrução objetiva semelhante a:

NEXT:
Implementar a renderização dos gateways do processo P004 usando
src/data/generated/processes/exportacao.json.
O parser já está concluído.
Não modificar scripts/extract-bizagi.ts salvo se um teste falhar.

Assim, uma próxima sessão conseguirá continuar.
